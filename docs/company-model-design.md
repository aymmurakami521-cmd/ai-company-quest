## 0. なぜ書くのか

現在のQuestは「event streamから畳み込んだactorの状態」までを描く read model です。
ここに記録するのは、その先にある製品像のうち **今のコードが将来それを妨げないか** を
判断するために必要な部分だけです。先行実装はしません。

### 0.1 中核にある考え

> ユーザーは**実現したい結果**を言う。ARKが必要な能力・人員・部署を判断し、安全に実行し、
> **証拠付きの結果**と**理解できる費用対効果**を返す。

ARKの価値は「AIのキャラクターが動くこと」ではありません。人間が負っている

- 詳細なpromptを設計する
- 誰にやらせるかを決める
- スキルと人員を組み合わせる
- 進捗を何度も確認する
- AI同士の受け渡しを調整する
- 本当に終わったのかを検証する
- 時間と費用を計算する

という段取りを肩代わりすることです。ゲーム画面は、その複雑な運用を人間が読める形にした
表現にすぎません。**画面が先にあるのではなく、運用が先にあります。**

### 0.2 長期の主要指標

> **追加の人間の指示なしに、証拠付きで完了した仕事の割合。**

補助指標（いずれも今回は計測しません）: 最初の結果までの時間 / 証拠付き完了率 /
1タスクあたりの人間の介入回数 / 自動復旧率 / パッケージ再利用率 / 削減時間 / 結果あたりのAI費用。

## 1. 正社員と臨時スタッフ

| | 正社員 | 臨時スタッフ |
|---|---|---|
| 在籍 | 継続 | 単発の仕事の間だけ |
| 人数上限 | **無し**（契約プランで制限しない） | 無し |
| 名前・見た目 | 自由に変更可能 | 自動生成、タスク中は不変 |
| タスク終了後 | 在籍したまま | メイン画面から退場。**履歴・成果物・実績は保持** |

- 正社員を一から作る・ARKが必要に応じて生成する・臨時から昇格させる・名前や見た目を変える・
  部署を異動する・過去の社員を復帰させる — **いずれもパッケージ利用回数を消費しません**（§6）。
- 臨時スタッフは同じタスク中、同じ名前・見た目・識別番号・一時所属チームを維持します。
- よく使われる臨時スタッフの正社員への昇格は、事前承認なしで構いません。追加後に
  「誰を・なぜ・何を担当するか」を簡潔に事後報告します。

### 1.1 自動整理

正社員数は無制限ですが、全員をメインオフィスへ出し続けません。

`稼働中 / 待機中 / 休憩中 / スキル習得中 / 一時休止 / リモート勤務 / 別拠点 / 長期非稼働 / 退職・アーカイブ`

- 長期間使われていない社員は画面上から整理してよい。
- **自動で完全削除しない。** 名前・見た目・設定・履歴・成果物を保持し、同じ状態で復帰できること。
- 「長期間」の具体的な日数は**未決定**。設定可能な構造にすること。

## 2. 内部識別子と表示情報（現行コードとの関係）

**現行コードはこの要件を既に満たしています。** 変更は不要です。

- 識別子は `actor_key` = `(session_id, agent_id)` のinjectiveな符号化（`src/domain/actor.ts`）。
- 表示名は `Desk.display_name` として別に導出される（`quest-view.js`）。
- キャラクターの見た目も `actor_key` のhashから決まるので、**名前を変えても見た目と履歴の
  結び付きは切れません**。
- 組織role（`agent_role`）と実行時type（`runtime_agent_type`）は既に別fieldです。
- model / provider / 実行権限のfieldは**存在しません**。したがって「このキャラクターは
  このmodel」という固定化も起きていません。

将来の課題として残るのは1点だけです: `actor_key` は **session-scoped** なので、
session をまたいで同一人物を指す識別子ではありません。継続在籍する正社員を導入する時点で、
`(employee_id) ↔ (actor_key)` の対応をどこが持つかを決める必要があります
（`org-snapshot-design.md` §4.2 の未決事項と同じ論点）。

## 3. 業務状態と表示上の居場所を分ける

将来は、同じ「待機中」でも表示上の居場所を変えます。

| 業務状態 | 表示上の居場所の例 |
|---|---|
| 短期待機 | 社内カフェ / 社員食堂 / コミュニティラウンジ |
| スキル習得中 | 社内ライブラリー / 研修室 |
| 集中準備 | 集中ブース |
| 一時休止 | 仮眠室 / ウェルネスルーム |
| 長期非稼働 | リモート勤務 / 別拠点 / 社員名簿・アーカイブ |

その他: 屋上テラス / 屋上庭園 / ストレッチスペース / ゲームスペース。

**規則**

- 業務状態と居場所を同じ値に固定しない（例: 業務状態=待機中、居場所=社内カフェ）。
- **休憩中のアニメーションのためにAI処理を動かさない。** 画面上では
  「状態: 待機中 / AI処理: 停止中 / クレジット消費: なし」のように実際の状態を確認できること。

**現行コードとの関係**: 席の座標は一覧の並び順だけで決まり、状態は色・marker・labelしか
変えません（`quest-world.js`）。居場所という概念自体が無いので、固定化もされていません。
外部hook wireには `HookFacility`（`desk` / `shelf` / `terminal` / `search-terminal` /
`antenna` / `meeting` / `portal`）が既に載っており、`hookAdapter.ts` が意図的に落としています。
将来はこのdropを解除するのが最短の接続点です。

## 4. プランモードと会議室 / オンライン参加

- 複数のAIが計画・議論・分担を行う場合は、関係する社員が**会議室**へ集まる表現を採る。
  会議室で確認できるようにするもの: 議題 / 参加者 / 進行役 / 検討中の内容 / 決定事項 /
  未解決事項 / 人間の判断が必要な事項 / 会議後のタスク / 議事録。
- 単独の簡単な計画は自席または集中ブースで表現する。
- 別部署・フロア・拠点・外部環境のAgentは、会議室モニターのワイプ等で遠隔参加を示す。
  表示するもの: 名前 / キャラクター / 所属 / 接続元 / 遠隔である旨 / 発言中 / 接続状態 /
  社内・外部の区別 / 閲覧・操作範囲。
- 臨時スタッフが多数参加する場合は、代表者またはチーム単位でまとめて表示できること。

## 5. ARKパッケージ（3階層）

| レベル | 中身 | 例 |
|---|---|---|
| **1. スキル本** | 既存社員に能力・仕事の進め方を付与する | 議事録作成の書 / 営業リスト作成の書 / WBS更新の書 / GitHubレビューの書 / 提案資料作成の書 |
| **2. 社員パッケージ** | role・初期スキル・進め方・品質確認方法を構成済みの社員テンプレート | 営業企画担当 / 品質管理担当 / 経営企画担当 / Google Workspace導入支援担当 |
| **3. 部署パッケージ** | 複数のrole・業務手順・設備・掲示板・部屋をまとめた部署テンプレート | 営業部 / 品質管理部 / カスタマーサポート部 / セキュリティ室 |

- スキル本はゲーム画面の本棚へ追加する。**一度導入したスキル本は、何人に付与しても、
  何度使っても追加の利用回数を消費しない。**
- 部署パッケージ導入時は、まずオフィス画面へ**部屋を追加**する。会社規模が大きくなった
  段階でフロア追加へ発展させる。

## 6. 契約プランが制限するもの / しないもの

制限対象は **未導入のARK公式パッケージを新しく導入する回数だけ** です。

**制限しないもの**: 正社員の人数 / 正社員の採用回数 / 臨時スタッフの生成 /
臨時スタッフの正社員昇格 / 社員の異動 / 名前・見た目の変更 / 独自社員の作成 /
独自部署の作成 / 導入済みパッケージの再利用。

**設けないもの**: ゲーム内通貨 / 採用費 / 給与 / 建設費。

契約プランで変えるのは「新規導入可能なパッケージ回数」「利用できるパッケージの種類」
「基本・専門・業種別などの利用範囲」の3つ。
**具体的なプラン名・回数・リセット周期は未決定**。設定可能な構造にすること。
上限に達しても、ARKが勝手に契約プランを変更しないこと。

## 7. パッケージ承認と権限承認は別のもの

### 7.1 未導入パッケージの導入前に表示するもの

1. パッケージ名 2. 種類 3. なぜ今回必要か 4. 導入すると何ができるようになるか
5. 何が自動化されるか 6. 今回消費する回数 7. 導入前の残り回数 8. 導入後の残り回数
9. 次回リセット日時 10. 新しく必要になる外部接続・権限

リセット日時は `2026年9月15日 0:00 日本時間` のように具体的に表示します。

選択肢: **今回だけ承認** / **導入せず既存能力で進める** / **次回リセットまで自動導入** /
**残り回数がなくなるまで自動導入**。

自動導入が許可されている場合は残り回数の範囲内で事前承認なしに導入でき、事後に
「導入したもの / 理由 / できるようになったこと / 残り回数 / 次回リセット日時」を報告します。

### 7.2 分離の規則（重要）

パッケージ導入の自動化が許可されていても、**以下は別の承認**として扱います。

- 新しい外部サービスへの接続 / Secret・認証情報の入力 / 閲覧範囲の拡大 /
  編集・送信権限の追加 / 顧客へのメール送信 / データ削除 /
  金銭・契約に直接影響する操作 / その他の高リスク操作

**パッケージ導入の許可だけで、新しい権限まで自動付与してはいけません。**

### 7.3 手動選択画面の表示

技術的な説明より「導入後に何が変わるか」を示します: 何ができるようになるか /
どの作業が自動化されるか / どんな場面に向くか / 必要な外部接続 / 必要な権限 /
現在の社員・スキルとの重複 / 見込まれる設定時間・実行時間・クレジット・人手作業の削減 /
推定の根拠と確度。

カードを見ただけで「このパッケージを導入すると何が自動化されるのか」が分かること。

## 8. 効果の表示（実測と推定を分ける）

`cost-governance-roi-design.md` の用語に従います。**実測値と推定値を混ぜないこと。**

| 実測 | 推定 |
|---|---|
| 実際のクレジット / トークン / 所要時間 / AI費用 / 再実行回数 | パッケージが無かった場合の使用量 / 人手作業時間 / 人件費換算 / 回避できたやり直し |

推定には必ず **根拠** と **確度** を付けます。

> クレジット削減見込み: 20〜30%
> 根拠: 同種タスク過去10件との比較
> 確度: 中

人件費換算は実際の現金削減とは限らないため `人件費換算で約4,000円相当` のように表示します。
**パッケージによってクレジットが増えた場合も隠さず**、品質・やり直し・確認時間を含めた
総合効果を表示します。

## 9. 現行コードの拡張点

将来これらを実装するとき、既存の仕組みのどこに載せられるかの記録です。

| 追加したいもの | 接続点 | 備考 |
|---|---|---|
| Agent種別（正社員 / 臨時）、居場所、パッケージID / version、アーカイブ状態 | `OPTIONAL_KEYS`（`src/domain/event.ts`） | 欠けたらnull、在れば必須keyと同じく検証。`runtime_agent_type` が実例。schema bump不要 |
| actorごとの保持情報 | `ActorState`（`src/domain/reducer.ts`）への加算 | snapshotがstateを丸ごと配信するのでclientへ自動的に届く。**client foldにも同じ規則を書くこと**（parity testあり） |
| 表示名・部署・役職などの人事情報 | `ActorDirectory`（`src/domain/actor.ts`） | 現在は `roles` のみ。streamではなく**起動時の別入力**として渡す設計（`org-snapshot-design.md` §2.1 と同じ考え方） |
| 居場所（会議室・カフェ等） | `hookAdapter.ts` が落としている `activity.facility` | `HookFacility` として外部wireに既に載っている。dropを解除するのが最短 |
| 新しいstatus | `STATUS_TOKENS` + `ACTOR_VISUALS`（`quest-view.js`）と `HOOK_EVENT_LIFECYCLE` | LIVEで点灯させるには lifecycle table にも行が要る |
| 成果物・証拠への参照 | **接続点なし** | 内部modelにもwireの19 keyにも該当fieldが無い。`run-event-contract`（Issue #22）で evidence kind を確定してから |

**しないこと**: 今使わないfieldを大量に先行実装すること。永続化データが存在しない
（stateは全てin-memoryでstreamから畳み直す）ため、後から足す方が安全で安いという判断です。
